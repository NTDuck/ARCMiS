# Survey 220926 — methodology × model sweep

Status: COMPLETE. All 180 cells ran (4 projects x 3 methods x 3
models x 5 reps), strictly sequential, 2026-09-22T19:00 to
2026-09-23T00:07 +07. Numbers below come from
`experiments/220926/results/aggregated.yml`.

## Executive summary

Agent-verified end-to-end success (cargo build + cargo test green in
the produced workspace) is rare and concentrated: 5 of 180 runs, all
on the smallest project (`fft`, 233 C LOC), all `monolith` (ReAct +
validator). The 27B pair works somewhat. The 2B model never succeeds.
`ledger` wrote 3 per-problem records, but every one is a manager
self-report over an empty workspace — no translated code, no compile.
`recode` never produced a record. The dominant failure modes are
turn-budget exhaustion (75 of 180) and malformed tool-call arguments
the ollama daemon rejects (23 of 180, plus 70 "other" errors
dominated by the same class).

## Survey design

- Grid: 4 projects x 3 methods x 3 models x 5 reps = 180 cells, one
  harness process per cell, strictly sequential.
- Projects (ReCodeAgent dataset, crust split, C to Rust): `fft` (233
  C LOC), `totp` (443), `cjson` (1101), `expr` (1110).
- Methods:
  - `monolith` — one ReAct agent (write + bash tools) plus a validator
    agent with a 14-turn budget.
  - `ledger` — manager-worker scaffold with shared workspace files
    (plan.md, tasks.json, notes.md) and the brainstorm-then-manage
    flow of arXiv:2608.26480 section 3.1, with a 14-turn manager
    budget.
  - `recode` — analyzer, planner, translator, validator loop per
    arXiv:2604.07341 Algorithm 1, with 40 turns per phase agent.
- Models (all ollama, one at a time, offloaded between every run):
  - `openbmb/minicpm5-2b:q8_0` (2B)
  - `qwen3.8:27b-mtp-q4_K_M` (27B official)
  - `smtek/Swift-Qwen3.8-27B:dflash2` (27B fine-tune)
- Excluded: `SparkLLM/Spark-X2.5-4B` — its `spark2_5` GGUF
  architecture fails to load in the local daemon.
- Scoring: the toolchain decides. After each run the harness reruns
  `cargo build` and `cargo test` in the produced workspace. The
  harness records agent self-reports but never trusts them.
- VRAM discipline: `--offload` unloads every resident model before and
  after each run, verified by polling `/api/ps` until empty.

## Failure analysis (180 runs)

| Class | Count | Share |
| --- | --- | --- |
| max_turns (budget exhausted mid-translation) | 75 | 42% |
| other (model-side protocol errors, empty streams) | 70 | 39% |
| invalid tool call arguments (daemon HTTP 500) | 23 | 13% |
| json parse of model output | 4 | 2% |
| toolchain-verified success | 5 | 3% |
| scored pass, manager self-report (empty workspace) | 2 | 1% |
| scored fail, manager self-report (empty workspace) | 1 | 1% |

Reading: the 2B model fails tool-call argument formatting at a rate
that makes agent-driven translation unreachable. For the 27B models,
the binding constraint is the turn budget: pipelines spend turns on
exploration and re-reading and hit 14 (monolith/ledger) or 40-per-
phase (recode) limits before producing a compiling workspace. The
multi-agent scaffolds divide the same turn budget across more
workers, so they exhaust it sooner relative to useful work.

## Conclusions

- Model capability dominates methodology choice at this scale: no
  method extracted success from the 2B model. Both 27B variants
  succeeded, with the fine-tune ahead on monolith (3 of 5 verified
  passes).
- Simpler orchestration wins here. Monolith's single-agent loop plus
  validator produced the only verified workspaces (5 of 60). Ledger's
  manager-worker scaffold wrote zero code in 60 attempts — its three
  "passing" records are manager self-reports over empty workspaces,
  caught only by post-sweep workspace inspection. Recode's four-agent
  loop compiled nothing. The ledger result also exposes a harness
  gap: the manager's validation summary can write a per-problem
  record without the toolchain ever seeing the workspace.
- Project size is the second axis: every verified success is on the
  233-LOC project. The three larger projects produced zero verified
  passes across 135 attempts.
- Turn budgets, not context windows, are the binding harness limit
  for 27B-class models on 200-1200 LOC C-to-Rust translation. 42% of
  all runs died on MaxTurnsError.
- Tool-call argument formatting remains the primary ollama-side
  reliability risk (13% hard daemon rejections plus a share of the
  39% "other" class).
